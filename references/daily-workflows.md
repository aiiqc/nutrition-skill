# 日常使用与状态

## 建档与选餐

先明确成员，不要求真实姓名或证件。每份文档只服务一个成员；`id`是稳定的本地标识。沿用已经回答的资料，未知保留未知。目标可同时含增肌、减脂、健康饮食，主目标尚未确定时让用户选当前优先方向，不许诺同时快速达标。

把已知事实放入最小 `profile` 并调用 `assess_profile`。返回 `pending` 时集中问最多三个当前高价值问题；资料不足也可帮助整理现有饮食，但不越过分流条件给个体化安全结论。年龄与健康限制影响路径；腰围、体脂、照片不作为所有人的必填项。当前没有生成个人热量目标的能力，不能以填齐身高体重为由承诺已经可以自动算目标。

`preferences`中的菜式、省事程度和场景独立：例如中式＋懒人＋外卖。厨房条件、预算或临时聚餐若契约没有对应字段，只作当前对话条件使用，不添加未声明的字段；不声称已经持久保存这些偏好。可以解释某候选为何不适合，并使用 `excluded_ids`换掉；不能为了匹配预算把硬限制删除。

调用 `next_meal`后优先显示：

1. 下一餐推荐的实际食物组合、怎么买或怎么准备。
2. 原样保留份量说明的准确含义；标明这是结构建议，不能附上未经计算的热量或宣称已满足目标。
3. 最多两个确实返回且可用的替换方向；没有候选就说明冲突与可调整的软条件，不凑数量。

用户要全天时，分别调用其需要的餐次，保持既有适用作息；不机械强制三餐。精细用户可把目录内、状态和份量明确的食品交给核心计算，菜单中其余食物另列未覆盖，不把小计叫整餐或全天合计。

已有明确适用的全天目标时，先区分用户自定与用户提供的专业要求；来源、适用成员或当前有效性不清时先补齐，不能将一个`source`字符串当作医学授权。用`check_day_plan`核对已量化计划。`coverage.expected_meal_ids`包含当天计划的所有用餐组，加餐、饮料、用油也要落在相应items内。只有用户明确确认整天计划完整时才设`confirmed=true`，不要因早餐午餐晚餐都存在就自动确认。

餐次不全、尚未量化或未被目录覆盖时保持`confirmed=false`并说明缺项；不把未知食品删掉后声称全天符合。未完整覆盖时，已知小计低于目标不等于全天不足，但已知部分超上限仍要指出。`plan_complete`只说明用户声明范围内的计划覆盖，不证明营养完整、医学适用或实际吃过；各营养素仍看`complete`，各限制看返回状态。没有给定限制时，成功只说明覆盖及计算有效。

## 计划和实际记录

先判断这句话在说打算吃还是已经吃。提出下一餐或替换方案不生成实吃。确定日期、成员和餐次后，按整餐证据分流：

| 用户陈述 | 操作与状态 |
|---|---|
| “计划中这些食物照量吃完了”，且整餐都有已核对食品和数量 | `record_actual`，`confirmed`，使用实际食品与数量。 |
| “这份可量化餐只吃了一半” | 如果明确指全部食物的一半且没有混合分配歧义，计算实际数量后用 `partial`；不是把原计划全量重复存入。 |
| “午餐米饭吃了八成”，其他食物未说明 | 粗记已知事实，或精细用户补问其余食物；不默认其他项目全部吃完。 |
| “吃了火锅，份量不清楚”、目录未收录的外卖、尚无克数的一碗饭 | `record_note`写 `journal`，保留 `quantity_status=unknown`或有依据的 `estimated`；不伪造食品ID与克数。 |
| “这餐没吃” | 明确 `not_eaten`；M2 items为空或省略。只表示该餐没吃，不能抹去当天别的食物。 |
| 未提该餐、只发尚未确认的照片 | 未记录／待确认；不转为零，不自动写 confirmed。 |

清楚的用户陈述一次输入即可完成确认。照片、包装文字或含糊匹配先提出候选，只追问影响结论的部分。没有把握时保存已知事实比虚构精确值更有用。

**同一成员、日期、餐次不能有两份互相矛盾的实吃。**已有 `days`中 confirmed／partial／not_eaten定量实吃时，不另建同餐 `journal`。要改定量记录，使用 `record_actual`；要把整餐改成粗记或从粗记转定量，先读取契约支持的纠正方式，当前不支持时明确停止转换，不手动删旧记录绕过校验。`journal`不参与精确营养总和。

粗记请求示例；这是虚构记录，用户确实确认后才发送：

```json
{
  "operation":"record_note",
  "document":{"schema_version":"m3-1","profile":{"id":"example_adult","storage":"temporary"}},
  "note":{"date":"2026-10-05","meal_id":"dinner","status":"partial","food_summary":"火锅，知道吃过但未称重","quantity_note":"份量不清楚","quantity_status":"unknown"}
}
```

定量记录依次取当前 `document.days[date]`、调用 M2操作、将返回的新 `state`放回同日期，再按已选存储方式处理。没有state时可以构造契约允许的餐次草稿并交由操作验证；不得把陌生菜名或文字份量塞入M2 item。`state.revision`与本地文件的存储 `revision`不是同一个版本号。

## 缺货、聚餐和锁定

结构推荐缺货时用 `next_meal`与排除ID重新取候选；已经建立的精确计划用 `replace_meal`，只改指定的可修改餐。保留已吃、明确未吃和锁定餐。模糊外食不能为了满足这个接口而临时假造营养库。

临时聚餐时帮助用户在其已知限制内选择可行食物组合，保留不明确的配料、油盐和份量。没有过敏证据或专业允许范围就不称“安全选择”。不建议提前挨饿、第二天补偿性断食或因为一次休息日机械大幅减餐。

新增过敏或专业要求时重新 `assess_profile`，适用的结构模板重新筛选；精确计划的单餐限制调用 `revalidate_plan`，全天限制调用 `check_day_plan`。锁定不阻止重新校验。`replace_meal`、`restore_plan`成功后也须重新核对全天；单餐通过不代表合计通过。每日临床总量不能直接当作每餐上限传入。

## 每周反馈与断档

确认实际观察天数、执行难度、饥饿、精神、训练及重要健康变化；未回答按契约保留 unknown 或省略，不默认没有变化。把事实交给 `weekly_review`，展示其理由和一两个最有用的执行变化。

明确“没有训练”记录为training=not_training，不改写成normal或unknown。执行了几天与执行难度是不同事实；提供adherent_days不代表已回答adherence，不据此猜测easy/mixed/hard。

当前只会返回保持目标并简化执行，或暂停调整并核对情况；不会重新计算个人热量、蛋白质或断食窗口。体重零散、记录缺失不能据此宣称“停滞”“代谢下降”或“减脂成功”。明显食欲下降或不明原因变轻时，按返回提示整理情况供专业评估，不下调目标。

断档回来时设置 `returning_after_gap`，确认目标、健康或生活条件是否变了，再从下一餐开始，不要求补齐历史。把周结果保存到 `reviews`只在本地保存已启用时调用实际保存操作，不能凭“每周”承诺后台执行。

## 家庭共餐与采购

先确认操作者有权代管相关成员；只载入本次需要的档案。每个人分别运行分流，分别决定菜式、专业要求与个人份量。专业支持可使用懒人展示，不会因此清空限制。

共同菜式可作为准备方式；个人份量不能由“全家共四人”或统一热量比例自动推出。无法兼容的过敏、食材或烹调要求应分开准备。家属说“父亲吃了一半”只更新父亲，不自动记录全家。

明确各人实际原料需求后，把目录中可量化的 items 交给 `aggregate_shopping`，`member_id`不可重复；同一成员的多个餐次先收集为一份items。输出保留生熟和逐人可食克重。不把生鸡胸与熟鸡胸并成同一采购量，不推导含骨带皮毛重、烹调损耗或整包数量。

目录未覆盖、尚未明确的食物在旁边列“待确认数量”，不填零、不从清单删掉。采购汇总不是家庭过敏安全证明，也不自动下单、发消息或共享成员健康资料。

## 锁定与解锁的明确更改

用户明确要求固定某餐或解除锁定时，先读取当前document，仅在内存中改变指定日、指定餐的locked布尔值，并把该state.revision递增一次。已经是所需锁定状态时不重复递增。不要更改items、actuals或其他餐的锁定。当前没有独立lock命令；用save_record的document校验、当前record_id与存储revision保存候选，不能直接改受管文件。用户只说换餐但原餐已锁定时，应先解释冲突，不能默默解锁。定量内容替换与旧计划恢复仍使用专门核心操作。

组合操作始终把上一步的最新state传给下一步，不能从最初revision重算或覆盖核心返回版本：

- 换餐后锁定：`replace_meal`成功返回revision=4的state，再在这个state上将原先未锁定的目标餐locked改为true并递增到5。
- 解锁后恢复：当前revision=5，先仅解锁指定餐并递增到6，再传入`restore_plan`，使用核心返回的revision=7。

一次`save_record`只增加一次文件存储revision，不能把上述两次计划变化合并成一次计划revision。组合失败则不保存候选，详见[保存与恢复](storage.md)。

## 周反馈的已知事实

可用adherent_days、hunger_days、hunger_times、weigh_ins_count、has_previous_week_baseline保留用户明确给出的执行天数、饥饿次数/时段、称重次数与基线情况。不要把“5天容易执行”写成“观察了5天”，也不要仅凭三次称重宣称存在体重趋势。没有给出的字段仍未知，当前不据这些观测改变热量目标。
