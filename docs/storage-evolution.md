# 长期本地记录与历史归档

长期使用采用**显式启用的 v3 分段 JSON 历史**。原来的 `nutrition-record-v2` 仍可读写，默认新建档案仍为 v2；不会因为升级软件、读取档案或保存失败而自动迁移，也不会静默删掉旧日期。

## 方案与复用依据

现有实现已有私有目录、目录级 `flock`、`record_id + revision` 并发检查、文件描述符路径遍历、`O_NOFOLLOW`、临时文件 `fsync` 与原子替换。本轮沿用这些机制。Python 官方的 [os.replace / fsync](https://docs.python.org/3/library/os.html#os.replace) 支持当前写入流程；[SQLite 事务](https://www.sqlite.org/atomiccommit.html)与 [Python sqlite3](https://docs.python.org/3/library/sqlite3.html)可用于数据库实现，但本轮没有引入数据库或后台服务的必要。开源 [TinyDB 并发讨论](https://github.com/msiemens/tinydb/issues/18)也说明，只锁单次读或写不足以保护完整读改写过程；本项目继续锁住整个操作。参考 [boltons 的原子文件保存](https://github.com/mahmoud/boltons)后，现有标准库实现足以满足需求，没有复制上游代码或增加依赖。

## 启用与日常保存

新增 Python 接口：

```python
archive_record(
    data_dir, member_id, expected_revision,
    consent, expected_record_id=None, keep_from_date=None,
)
```

必须先读取当前档案，取得准确 `record_id` 和 `current_revision`。只有用户同意启用长期归档，并同意本次日期范围时，才传入 `consent=True`。初次存储同意不自动等于同意移出旧日期。

- 没有 `keep_from_date`：完整归档当前活动历史，将完全相同的当前文档保存为下一修订。资料内容不变，修订数加一，`record_id` 不变。
- 有 `keep_from_date="YYYY-MM-DD"`：先完整归档此前文档，再从新活动文档移出严格早于该日期的 `days`、`journal.date`、`reviews.as_of` 和 `target_reviews.as_of`。当天及之后的记录保留；个人资料、当前 `planning` 和其他合法顶层字段保留。移出的内容仍存在历史版本中。
- 返回 `history_preserved=True`、使用的截止日期及 `moved_out_of_active_document` 各类数量，供宿主准确说明实际结果。

启用 v3 后，原 `save_record` 接口保持不变：仍须同意保存及提交上次读取的 `record_id`、修订号。每个活动段最多 50 次修订或 4 MiB，达到边界时，下一次保存先将完整旧段归档，再开始新段。归档按**包含封装字段的实际序列化字节数**分段，因此一份恰好 4 MiB 的合法 v2 历史也可以迁移，不会因新增字段卡住。全局修订号持续递增，没有重置或覆盖历史。

单份业务文档原有的日期、日志和反馈容量限制继续有效。在这些限制接近之前，应向用户解释准确截止日期，显式调用归档；不能在普通保存时自行移出记录。归档不会增加目录、食品或健康规则的适用范围。

## 查看与导出

`load_record(data_dir, member_id, version=None)` 仍可读取当前或指定的任意历史修订。v3 返回：

- `current_revision`：当前并发检查版本；即使读取旧修订，也不使用旧修订号直接覆盖当前档案。
- `history_range`：全部历史的首末修订号。
- `available_versions`：仅当前主文件内活动段的版本号列表。极大文档直接归档时，此列表可以为空；最新版本仍可通过 `load_record` 正常读取。
- `available_versions_truncated=True`：列表没有穷举归档历史；不能据此声称旧版本不存在。

`export_record(data_dir, member_id, start_version=None, limit=None)` 返回结构化内容，不自行写导出文件、上传或发送资料。

v2 不带新参数时保留原来完整 `record` 返回格式。v2 显式分页或 v3 导出均返回 `scope="history_page"`、`versions`、`first_version`、`last_version`、`total_versions`、`next_version` 和 `export_complete`。默认从版本 1 开始，一页最多 50 版；历史条目载荷达到 8 MiB 时会提前结束一页。继续使用 `next_version`，直到它为 `None`。

`export_complete=True` 只表示**这一响应本身**从版本 1 覆盖到当前末版。多页导出的每页可能都是 `False`；宿主只有在页序无缺口、最后 `next_version=None`，且每页 `record_id` 和响应顶层 `revision` 完全一致后，才可宣称这次汇总包含完整历史。并发保存或删除重建导致标识/版本变化时，不混合不同快照，重新读取并导出。单独备份最新活动文档不是全历史备份。

## 文件布局、失败与恢复

主文件仍是 `<member_id>.json`。归档段是同目录下带点前缀的管理文件，名称包含成员、`record_id`、准确起止版本与 SHA-256。主文件仅引用系统生成的准确名称；读取历史时同时校验内容身份、连续版本、文档结构和 SHA-256。普通当前读取不等于对全部旧段做了完整性扫描；完整分页导出会逐段校验所读取的历史。

极限单版本可使用 `nutrition-archive-v1` 紧凑封装，仍保留 `record_id` 与完整版本条目；成员和范围由准确文件名、主文件引用、文档 `profile.id` 与条目修订号共同校验。当当前文档加历史索引超过主文件容量时，新修订也直接归档，主文件只保留连续索引、`versions=[]` 和 `first_revision=current_revision+1`。读取最新版本、继续保存、按日期归档、分页导出与删除均支持这种布局。每个物理文件仍不超过 4 MiB，没有借迁移提高上限。

存储要求仍是受支持的本地 POSIX 文件系统：目录为用户所有的 `0700`，文件为 `0600`。拒绝符号链接、硬链接、非普通文件、路径穿越和不私有的现有权限。软件不会自动修改既有路径权限。归档是应用层只追加：文件所有者仍有能力修改文件，校验和用于发现意外或外部修改，不是加密或数字签名。没有原始对话、照片、录音或转录字段。

写入顺序为：写新归档并同步 → 原子替换主文件并同步。主文件替换前失败，旧档案不变；可能留下完整但未引用的归档段。后续明确重试会先读取当前状态，仅在该段身份、完整结构和校验和都一致时复用，不能覆盖同名异常文件。主文件替换后目录同步失败返回 `storage_durability_uncertain`；必须先核对当前版本，不能盲目重试保存。

不能只搬走主文件而遗漏点前缀归档。旧版程序不会理解 v3；需要保留能读取 v3 的版本及全部管理文件，或者用新版程序导出结构化历史。不会自动将 v3 回写为 v2，也不会自动导入来历不明的档案。

## 删除范围与中断恢复

`delete_record` 签名不变，仍要求当前 `record_id`、修订号及准确 `confirmed=True`。删除范围为该成员当前档案，以及**同一 record_id、同目录下经过完整身份与校验和验证的归档段**，包括此前失败遗留的完整段。其他成员、其他 record_id、外部导出/备份、宿主会话和非管理文件不在范围内。不会递归删除目录，也不承诺安全擦除或删除其他系统的副本。

删除前先校验全部目标；遇到缺失或损坏的正常归档、符号链接或占用该档案命名空间的异常文件时，返回错误而不删除。删除开始后，主文件先变成持久化的 `nutrition-record-delete-v1` 恢复标记，再移除已核对归档，最后移除标记。**写入删除标记即进入删除流程，当前文档不再可恢复为活动档案**。如果中途失败，普通读取、保存、归档和导出返回 `storage_deletion_pending`。用户确认继续后，使用同一 `record_id` 和修订号恢复删除；已经删掉的段允许缺失，不会删除新建或其他成员档案。

## 验证与实际边界

合成临时目录测试覆盖：v2 原行为；128 次连续修订及跨段逐版读取；全历史分页导出；v2 第 50 版显式转入长期模式；满 1000 条活动日志归档后继续保存；日期边界；并发冲突；磁盘满；归档成功而主文件切换失败；损坏内容与符号链接；删除中断；同步结果不确定后的恢复。另外，使用真实 4,194,304 字节上限测试多版本 v2 和单版本 v2 两种边界，确认全部旧版全文不变、裁剪范围正确、可以继续保存和导出、每个物理文件仍在上限内。没有读取、迁移或删除用户真实档案。

这不是无限容量承诺。单段/主文件仍最多 4 MiB，主文件中的归档索引也受此限制；修订号最多 `2**31-1`，实际磁盘空间仍可能耗尽。达到边界时明确报错，历史不会被自动回收。文件按完整文档版本保留，空间随使用增加；数据量特别大、多设备共享或需要加密同步的产品，应另行设计经过迁移验收的存储后端。
